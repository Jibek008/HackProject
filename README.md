 # SQL Injection Lab

Учебная изолированная лаборатория для наглядной демонстрации уязвимости **SQL Injection** и способов её предотвращения.

> **Только для обучения.** Лаборатория запущена в изолированном окружении, использует только вымышленные данные. Не применять приёмы из этой лабы к реальным системам.

## 1. Цель

Показать:
- В чём суть SQL-инъекции (когда пользовательский ввод попадает в текст SQL-запроса)
- Как можно обойти авторизацию и извлечь данные через уязвимый эндпоинт
- Почему параметризованные запросы (prepared statements) надёжно защищают от SQLi
- Разницу между Error-based, Boolean-based Blind, Time-based подходами

## 6. Как проводить атаку (пошагово)

Откройте **http://127.0.0.1:5000**. Там есть дашборд со всеми демо.

### A) Классический обход авторизации

1. Перейдите во вкладку **Vulnerable Demo** → **Login**
2. Попробуйте обычный логин: \student\ / \lab_pass_123\ — должен пройти
3. В поле **Username** введите:
`sql
' OR '1'='1' --
`
В поле **Password** можно оставить любое значение.
4. Нажмите "Login". Авторизация **обойдена** — запрос сформирован конкатенацией.

### B) Сравнить с защищённым вариантом

1. Перейдите во вкладку **Secure Demo** → **Login**
2. Введите тот же пейлоад: \' OR '1'='1' --\
3. Доступ **запрещён**. Ввод трактуется как данные благодаря плейсхолдерам \?\.

### C) Boolean-based Blind

1. **Vulnerable Demo** → **Blind Probe**. \1=1\ → true, \1=2\ → false
2. **Secure Demo** → **Blind Probe** с теми же условиями — канал закрыт

### D) Автоматическое извлечение секрета

1. **Vulnerable Demo** → **Extract Secret** — нажмите "Extract", секрет будет собран посимвольно
2. **Secure Demo** → **Extract Secret** — извлечение невозможно

### E) Time-based

1. **Vulnerable Demo** → **Time-based** с большим \workload\ — задержка заметна
2. **Secure Demo** → **Time-based** — задержка незначительна

### F) Error-based

1. **Vulnerable Demo** → **Error-based** — при некорректном вводе показываются детали ошибки
2. **Secure Demo** → **Error-based** — нейтральное сообщение

## 7. Как объяснять разницу (для презентации)

- **Уязвимый:** \"SELECT ... WHERE username = '" + username + "'"\ — данные и код смешаны
- **Защищённый:** \cursor.execute("SELECT ... WHERE username = ?", (username,))\ — шаблон SQL отделён от значений
- **Суть:** параметризация превращает пользовательский ввод из "части SQL-кода" в "литеральное значение"

Сравните блок "SQL запрос" в UI для одинакового пейлоада — разница очевидна.

`powershell

## 9. Рекомендации по защите

**Никогда:**
- Не склеивать пользовательский ввод с SQL
- Не выводить детали SQL-ошибок пользователю
- Не хранить пароли в открытом виде

**Всегда:**
- Использовать **параметризованные запросы** (prepared statements)
- Использовать ORM корректно
- Применять **белые списки** для имён таблиц/колонок
- Давать БД-пользователю **минимальные привилегии**
- Возвращать **единые нейтральные** сообщения об ошибках
- Хешировать пароли (bcrypt/argon2)
