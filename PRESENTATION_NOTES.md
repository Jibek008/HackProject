## Цель выступления
Показать на практическом примере, почему конкатенация пользовательского ввода с SQL приводит к SQL Injection, и как параметризованные запросы предотвращают эту уязвимость.

## Подготовка к демонстрации
- Открыть консоль в `C:\Users\user\PycharmProjects\Hack`
- Убедиться, что активировано `.venv` (при необходимости)
- Запустить: `py app.py`
- Открыть браузер: `http://127.0.0.1:5000`

## Ход защиты

### 1. Вступление (0,5–1 мин)
- Кратко: «SQL Injection Lab — локальная учебная лаборатория. Демонстрирую принцип SQL Injection и сравнение с защищённым подходом».
- Указать: работает **только** на `127.0.0.1`, использует **вымышленные** данные.

### 2. Описание архитектуры (0,5–1 мин)
- **Единая БД** SQLite с тремя вымышленными пользователями.
- Два параллельных обработчика над одной БД: **Vulnerable** (демонстрационный) и **Secure** (рекомендуемый).
- API: `POST /api/vulnerable/login`, `POST /api/secure/login`. На фронте — тёмный dashboard.
- Ключевое: **Vulnerable** намеренно небезопасен для учебной демонстрации.

### 3. Демонстрация корректного входа (0,5–1 мин)
- **Vulnerable Demo**: ввод `student` / `lab_pass_123`. Показать **сгенерированный SQL**:
  ```sql
  SELECT id, username, role FROM users WHERE username = 'student' AND password = 'lab_pass_123'
  ```
- Пояснить: запрос вернул ровно 1 строку, авторизация успешна.
- **Secure Demo**: те же данные. Показать **параметризованный шаблон**: `WHERE username = ? AND password = ?` и параметры. Результат аналогичен.

**Вывод:** при корректных данных оба варианта ведут себя одинаково.

### 4. Демонстрация SQL Injection (1–2 мин)
- Перейти в **Vulnerable Demo**.
- Нажать кнопку «Пробросить payload: ' OR '1'='1' --» (или ввести вручную).
- **Обратить внимание на SQL**:
  ```sql
  SELECT id, username, role FROM users WHERE username = 'student' OR '1'='1' --' AND password = 'anything'
  ```
- Пояснить: после `OR '1'='1'` условие **всегда истинно**. `--` закомментировал оставшуюся часть `AND ...`.
- **Результат:** `row_count >= 1`, вернулись **все** пользователи (или >=1). **Логика авторизации обойдена**.
- **Причина:** пользовательский ввод **встроился в SQL-код**. СУБД восприняла его как синтаксическую конструкцию.

### 5. Сравнение с защищённым режимом (1 мин)
- Перейти в **Secure Demo**. Ввести тот же payload.
- Показать: запрос остался **шаблоном** `username = ? AND password = ?`. Параметры переданы отдельно.
- **Результат:** `success=false`, `row_count=0`. Обход **не удался**.
- **Объяснение:** в параметризованном запросе `?` — это **значение**, а не фрагмент SQL. Строка `student' OR '1'='1' --` ищется **буквально** как имя пользователя. СУБД **не** интерпретирует кавычки/OR/-- как код.

**Формулировка:** «Код и данные разделены. Именно поэтому параметризованные запросы защищают от SQL Injection».

### 6. Автоматические тесты и выводы (1–1,5 мин)
- Кратко о тестах: проверяют успешный вход, отказ при неверных, **наличие** уязвимости **только** в vulnerable, **отсутствие** обхода в secure, корректную обработку некорректного ввода.
- **Фактические результаты:** все 9 тестов **PASSED** (см. README).
- **Главный вывод:** **Никогда** не собирать SQL конкатенацией пользовательского ввода. **Всегда** использовать параметризованные запросы (prepared statements).

### 7. Ограничения и рекомендации (0,5 мин)
- Лаборатория **только локальная** (127.0.0.1).
- Vulnerable-версия — **исключительно учебная**.
- В реальных приложениях: параметризация, минимальные привилегии БД, аккуратная обработка ошибок, корректное хранение паролей.

## Ключевые фразы для защиты
- «SQL Injection возникает, когда пользовательский ввод становится частью исполняемого SQL-кода».
- «В параметризованном запросе данные передаются отдельно от SQL-шаблона. СУБД не интерпретирует их как ключевые слова».
- «В vulnerable-режиме мы сознательно показали эффект. В secure-режиме показали корректное поведение».
- «Данная лаборатория демонстрирует разницу экспериментально, а не декларативно».
